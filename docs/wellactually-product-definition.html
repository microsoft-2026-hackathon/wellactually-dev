01 / TARGET USER

AI-native 주니어 개발자

Coding Agent와 함께 개발을 시작해, 이전부터 축적된 개발 방법론·설계 원칙·실무 노하우를 직접 적용해 볼 기회가 부족했던 주니어가 핵심 타깃입니다. 페어 프로그래밍 경험이 없거나 부족하고, 개발 과정에서 무엇을 고려해야 하는지 익히려는 사람을 위한 제품입니다.

할 수 있는 일

개발과 배포

  • 코딩 에이전트에게 기능 구현을 요청합니다.
  • 도구와 서비스를 연결해 동작하는 제품을 만듭니다.
  • 개발 환경과 배포 절차를 활용합니다.
채우고 싶은 경험

엔지니어링 판단

  • 왜 그 방법을 선택하는지, 다른 방법은 무엇인지.
  • 어떤 전제·예외·변경 영향을 확인해야 하는지.
  • 무엇부터 조사하고 어디까지 맡겨야 하는지.

개인 프로젝트, 스스로 만든 학습 프로젝트, 회사 제품 등 사용자가 이미 진행 중인 프로젝트에서 활용합니다. Wellactually가 교육용 프로젝트를 별도로 제공하는 방식은 아닙니다.

모든 주니어가 이 문제를 겪는다는 뜻은 아닙니다. 이 공백을 느끼고 실제 작업을 통해 채우려는 사람이 초기 타깃입니다. 숙련자도 낯선 영역에서 도움을 받을 수 있지만, 제품의 첫 기준은 이 주니어의 경험입니다.

03 / WHY PAIR PROGRAMMING

페어 프로그래밍의 학습 원리

개발 방법론이나 설계 원칙을 아는 것과, 실제 작업에서 언제 어떻게 적용할지 아는 것은 다릅니다. 페어 프로그래밍에서는 현재 코드와 요구사항에 그 원칙을 적용해 보고, 놓친 조건을 검토하며 선택의 결과를 확인합니다. 이 과정을 통해 다음 작업에도 쓸 수 있는 노하우를 익히려는 것입니다.

전통적인 페어 프로그래밍에서는 두 개발자가 같은 작업을 두고 구현하는 Driver와 방향·검토를 맡는 Navigator 역할을 나누고 교대합니다. Wellactually는 그 구성을 그대로 복제하기보다, 판단을 함께 드러내고 피드백받는 경험을 AI 시대의 역할 분담으로 재구성합니다.

  1. 01 · 맥락

    내 문제에서 출발

    사용자가 이미 해결하려는 작업이 있습니다. 추상적인 지식이 구체적인 선택과 연결됩니다.

  2. 02 · 사고의 표현

    이유를 말해 보기

    현재 생각을 설명하면서 가정과 모르는 부분이 드러납니다.

  3. 03 · 피드백

    다른 관점과 비교

    페어의 질문·반례를 계기로 놓친 조건을 검토하고 판단을 바꿉니다.

  4. 04 · 적용

    실행 결과와 연결

    내린 판단을 작업 지시로 표현하고, 관찰한 결과를 해석합니다.

제품의 기본 전제

맥락 속 판단 연습

“항상 캐시를 넣어라”가 아니라 “병목·최신성·운영 비용을 보고 판단한다”는 사고 과정을 경험합니다. 방법론과 설계 철학은 외울 정답이 아니라 선택에 쓰는 관점입니다.

인간 페어링의 연구 맥락

교육적 근거와 한계

인간 페어 프로그래밍의 교육 연구에서는 수강 유지와 과제 품질의 이점이 관찰됐습니다. 다만 대표 연구의 개인 기말시험 점수 차이는 유의하지 않았고, 무작위 개인 배정도 아니었습니다. AI 페어의 효과를 그대로 증명하는 근거는 아닙니다. [R4]

별도 교육과정을 만들지 않습니다. 배워야 할 기초 지식 전체를 세션 안에서 가르치려 하지 않습니다. 현재 판단을 이어가기 위한 최소한의 설명을 제공하고, 더 깊은 공부가 필요한 부분은 별도로 남길 수 있습니다.

04 / WHY PAIR PROGRAMMING WITH AI

AI 페어링과 역할 분담

AI가 실제 작업의 맥락에서 놓친 가정과 검토할 지점을 짚어, 사람이 개발 방법론과 설계 원칙을 적용해 보도록 돕는 구성입니다. 사람은 이유를 이해하고 방향을 선택하며, 구현은 Driver에게 맡깁니다. 판단에 참여하고 피드백받는 경험을 필요할 때 선택할 수 있게 하려는 제안입니다.

역할을 분리하는 이유

구현과 판단 연습의 분리

Driver와 계획부터 논의하는 방식도 가능합니다. 차이는 AI의 개수가 아니라, 완료를 위해 사고까지 위임할 수 있는 흐름과 중요한 판단을 사람에게 남겨두는 흐름의 차이입니다.

Driver를 일부러 무능하게 만들어 Coach의 필요성을 만들지 않습니다. 맡길 범위와 조건은 사람이 연습하고, 그 안의 구현은 Driver가 처리합니다.

아직 검증할 부분

개입과 학습 효과

AI 생성 코드에 대해 설명·예측·결정을 요구한 연구에서도 독립 평가의 유의한 향상을 확인하지 못한 경우가 있습니다. 별도 Coach와 선택적 세션이 더 나은 판단으로 이어지는지는 실제 사용으로 확인해야 합니다. [R5]

별도 모드가 아니라, 현재 필요한 판단에 따른 대화 방식
페어링 방식 Coach가 드러내는 판단 사람이 해 보는 일
문제 정의 · 핵심 해결책 전에 문제·근거·목표가 명확한가. 관찰과 추측을 구분하고 무엇을 개선할지 정함.
설계 논증 · 핵심 선택의 이유, 대안, 제약, 운영 비용은 무엇인가. 트레이드오프를 이해하고 방향과 재검토 조건을 선택.
작업 위임 설계 · 핵심 한 번에 어디까지 맡기고 무엇으로 확인할 것인가. 범위·제약·완료 기준을 직접 지시로 작성.
탐색·디버깅 · 필요시 어떤 관찰로 원인 가설을 구분할 수 있는가. 조사를 요청하고 결과를 보고 가설을 수정.
명세·반례 · 필요시 경계 입력·동시 실행·실패 순서에서 맞는 동작은 무엇인가. 기대 결과를 결정하고 설계·검증 기준에 반영.

Coach의 원칙: 현재 결정에 중요한 질문부터 하나씩. 이미 아는 것은 반복하지 않기. 모르면 필요한 만큼 설명하기. 이유와 위험을 이해했으면 진행하기. 새로운 근거 없이 같은 반대를 반복하지 않기.

05 / USER EXPERIENCE

사용자 경험

하나의 세션은 전체 개발 수명주기를 강제로 따라가지 않습니다. 이번에 함께 검토할 부분만 고르고, 필요하면 실행과 결과 확인까지 이어갑니다.

대표 진행 순서 · 조건에 따라 생략·반복·종료할 수 있음
시점 사용자 행동 서비스 반응 / 남는 것
1. 페어링 선택 Coach와 대화를 시작하고, 작업 맥락과 공유할 자료의 범위를 정함. 사용자가 공유한 맥락으로 Coach 대화를 시작. Driver 연결을 먼저 요구하지 않으며, 다른 대화나 자료를 임의로 수집하지 않음.
2. 세션 초점 “캐시를 넣으려는데 고려할 것을 모르겠다”처럼 현재 고민을 설명. 함께 볼 판단과 현재 근거·미정을 정리. 사용자가 빈틈을 전부 알고 올 필요 없음.
3. 논의 Loop·위임 Coach와 근거·가정·대안·제약을 검토하고 작업 범위·완료 기준을 정함. Driver에 맡길 때 작업 대화를 연결하고 지시를 직접 작성·전송. 질문·답변과 조건 수정을 반복. Driver에게 지시를 보내면 논의 Loop의 한 회전이 끝나고, Driver가 요청 범위의 작업을 수행.
4. 결과 공동 리뷰 Driver의 결과를 Coach와 함께 확인하고, 목표와의 차이·새로운 조건·다음 작업을 논의. 공유 범위 안의 결과와 근거를 사람과 Coach가 함께 참조. 통과·실패·미검증을 구분하고 리뷰 내용을 다음 논의 Loop에 반영.
5. 페어링 종료 이해가 충분해졌거나 시간·피로·보류 이유로 세션을 끝냄. Coach 관찰·자동 개입을 중지. 구현이 남아 있어도 가능하며 Driver 작업은 별도로 유지.
6. 지식 정리 세션 보고서를 확인하고, 자신의 프로젝트 작업으로 돌아감. 확보된 기록을 바탕으로 판단 변화·재사용할 관점·미정을 HTML로 정리. 저장 위치는 사용자가 선택.
EXAMPLE / ONE REALISTIC TASK

상품 목록 캐시 도입

“상품 목록이 느려서 Redis 캐시를 넣으려고 해.”

설명을 위한 가상 사례입니다. p95 800ms·TTL 1분·단일 인스턴스는 예시의 가정이지 측정값이나 권장 설정이 아닙니다. 대화는 사용자가 직접 생각하고 작성한 장면을 보여주며, 자동 지시문 생성 기능이 아닙니다.

A문제와 제약 확인문제 정의 + 설계 논증

사람 → Coach

설명 가공이 대부분의 시간을 써. 목록 p95를 800ms 안으로 줄이고 싶어.

Coach

캐시가 된 값은 어느 정도 오래돼도 괜찮아? 설명과 가격에 같은 기준을 적용할 수 있어?

사람

설명은 1분까지 괜찮지만 가격과 재고는 안 돼. 응답 전체를 캐시하면 안 되겠네.

Coach

그럼 캐시 대상부터 나눠 보자. 지금 운영 조건에서 Redis 말고 비교할 방법도 있을까?

사람에게 남는 판단

목표
Redis 도입이 아니라 응답 시간 개선.
발견한 조건
변경 빈도와 오래된 값을 허용하는 시간은 다름. 데이터별 최신성 요구를 구분해야 함.
방향
단일 인스턴스라는 조건에서 내부 캐시와 가공 최적화도 비교. Coach는 선택을 확정하지 않음.

병목 근거가 없다면 이 대화의 답을 지어내지 않습니다. 사람이 먼저 확인할 계측·조사 작업을 정해 Driver에게 맡깁니다.

B조사와 설계 수정작업 위임 + 탐색 + 설계 재검토

09 / REASONABLE QUESTIONS

주요 질문과 답변

제품의 목적을 바꾸는 비판과 실제 사용 중 튜닝할 문제를 구분합니다. 반론을 없애기보다, 어떤 선택을 했고 무엇을 더 확인해야 하는지 설명합니다.

그냥 Driver와 계획부터 논의하면 안 되나요?

가능합니다. 같은 질문을 한다고 같은 학습 경험이 자동으로 생기는 것은 아닙니다. 일반적인 사용에서는 결과를 얻기 위해 사고까지 위임할 수 있습니다. Wellactually는 중요한 판단을 사람의 역할로 남기는 페어링 경험을 의도적으로 구성합니다.

차별성은 두 AI의 존재가 아니라, 다음 유사 작업에서 사용자가 Coach 없이 더 잘 판단하고 지시하는지로 검증합니다. 별도 Coach의 추가 효과는 아직 제품 가설입니다.

내가 무엇을 모르는지 알아야 Coach를 찾을 수 있지 않나요?

빈틈을 정확하게 진단할 필요는 없습니다. “이 설계가 맞는지 모르겠다”, “무엇을 고려해야 할지 모르겠다”면 시작할 이유가 충분합니다. 함께 볼 판단을 발견하는 것이 세션의 일부입니다. 모든 작업을 감시해 자동으로 불러오는 서비스가 기본 전제는 아닙니다.

Coach의 답을 Driver에게 옮기는 중계자가 되지 않나요?

그렇게 되면 목적에 어긋납니다. Coach는 완성된 지시문을 제공하고 전송만 요구하지 않습니다. 사람은 이유와 조건을 이해한 뒤 자신의 말로 지시합니다. 반면 코드·로그·기존 결정은 공유 문맥으로 연결해 판단은 남기고 자료 전달 노동은 줄입니다.

Coach가 모든 내용을 가르쳐 줘야 하나요?

아닙니다. 주된 역할은 놓친 전제와 고려할 지점을 드러내는 것입니다. 현재 판단에 필요한 최소한의 설명·예시는 제공하되, 기초 이론 전체를 세션에서 강의하려 하지는 않습니다. 더 공부할 부분은 보고서에 별도로 남길 수 있습니다.

결국 코딩 에이전트 대신 Coach에게 의존하게 되지 않나요?

그 가능성을 사용 빈도만으로 없앴다고 말할 수는 없습니다. 다만 제품은 선택적이고, 익숙한 작업까지 붙잡지 않습니다. 별도의 강제 졸업 시험보다 다음 비슷한 작업에서 스스로 조건을 찾는지를 봅니다. 사용 감소가 성장인지 피로로 인한 이탈인지는 구분합니다.

Coach가 틀리면 어떻게 하나요?

사람과의 페어링도 무오류를 보장하지 않습니다. 사용자는 납득하기 전까지 질문하고 근거를 확인하며 제안을 거절할 수 있어야 합니다. 제품이 그 태도를 대신 만들어 주겠다고 약속하지 않습니다.

동시에 Coach에는 근거·불확실성을 밝히고, 반박을 받으면 가정을 수정하며, 잘못된 결론을 정정할 책임이 있습니다. 최종 판단이 사람에게 있다는 이유로 이 책임을 없애지 않습니다.

페어링하면 일이 느려지고, 질문이 끝없이 늘어나지 않나요?

생각을 설명하는 시간은 들 수 있습니다. 그래서 매 작업에 강제하지 않습니다. 학습을 위한 사고와 불필요한 대화를 구분하고, 이미 확인한 내용이나 새 근거 없는 반대를 반복하지 않도록 페르소나·instruction을 조정합니다.

사람이 방향을 정했거나 조사로 분리했거나 위험을 이해하고 보류했다면 진행합니다. 중요한 기준은 무조건 빠름이나 많은 질문이 아니라 시간을 들일 가치가 있는 판단 경험입니다.

세션을 끝내면 구현도 중단되나요? 보고서를 읽으면 배운 건가요?

둘 다 아닙니다. 페어링 종료는 Coach의 관찰·자동 개입 종료이며, Driver 작업의 취소나 완료를 뜻하지 않습니다. 보고서는 그 시점까지의 기록을 정리합니다. 보고서의 존재도 학습을 증명하지 않습니다. 다룬 내용, 사용자가 표현한 이해, 실제 검증한 사실을 나눠 기록합니다.

11 / SOFTWARE ARCHITECTURE · BRIEF

소프트웨어 아키텍처

우선 구현안 · 통합 실행 검증 전 VS Code 확장으로 구성합니다. Driver는 기본 Copilot Chat에서, Coach는 별도 화면과 SDK 세션에서 동작합니다. 기본 UI에서 Custom Agent를 선택하는 것과 실행 하네스는 구분하며, 세션 관찰의 초기 검증 대상은 Agent Host 기반 Copilot입니다. [T1]

  1. 1 · Driver는 기존 환경에

    Custom Agent로 역할을 제공하고 기본 입력·도구·승인 UI를 유지합니다. Coach 지침을 Driver의 공용 지침에 섞지 않습니다. 수동 승인을 확인할 초기 검증 환경은 Folder + Manual permissions입니다. 자동 승인 환경도 있으므로 실제 권한 모드를 확인합니다. [T1] [T2]

  2. 2 · 선택한 세션만 읽기

    초기 논의는 Coach와 시작하고, Driver에게 작업을 맡길 때 관찰할 대화를 연결합니다. Observer는 공유 범위 안의 기록·상태·결과를 Coach도 참조할 수 있게 합니다. 읽기 동작만 어댑터에서 허용하며, Host가 강제하는 읽기 전용 자격 증명까지 보장된 것은 아닙니다. [T3]

  3. 3 · 별도 Coach와 문맥

    Copilot SDK의 독립 세션과 WebviewView를 사용합니다. 관련 근거만 전달하며 자동 평가는 페어링 중에만, 중복과 호출량을 제한합니다. [T4] [T5]

  4. 4 · 역할보다 강한 권한 경계

    Coach에 Driver 전송·취소·승인·편집 도구를 제공하지 않습니다. 관련 코드·관찰 스냅샷 읽기만 허용하는 구성을 시험합니다. 페르소나만으로 도구 권한이 제한되지는 않습니다.

  5. 5 · 종료 후 지식 컴파일

    사람이 끝내면 관찰·자동 코칭을 정리하고 기록 범위를 고정합니다. 출처가 있는 보고서 데이터로 HTML을 만들며, 임의 스크립트·명령 링크는 출력하지 않습니다. 저장·재시도는 사용자 선택입니다.

  6. 6 · 실패와 저장을 명확하게

    연결 단절·잘린 기록·생성 실패를 완료로 숨기지 않습니다. 원본 기록을 무조건 저장하거나 모두 모델에 보내지 않습니다. 공유 동의·보관 기간·삭제·모델 비용은 구현 시 확정해야 합니다.

가장 먼저 검증할 기술 조건: 실제 대상 VS Code에서 선택한 Driver 세션에 연결하고, 과거·현재 대화 및 도구 결과를 필요한 범위까지 읽을 수 있는가. 숨겨진 모델 내부 사고나 무제한 원본 로그에 접근한다는 뜻은 아닙니다. 지원되지 않으면 그 상태를 알리며, 파일 변경이나 요약만 보고 전체 세션을 읽었다고 주장하지 않습니다.

초기 범위는 텍스트 기반입니다. 음성, 미전송 초안 가로채기, Coach의 테스트 직접 작성은 필수 기능으로 두지 않습니다. Native 로그인과 SDK 인증의 자동 공유, 별도 모델 호출의 무료 사용도 가정하지 않습니다.

세부 구현 방식과 기술적 검증은 별도의 기술 구현 문서에서 다룹니다.
